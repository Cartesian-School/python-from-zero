Документация, версия и первый релиз

MAJOR.MINOR.PATCH, CHANGELOG.md и тег версии — проект получает точку, к которой можно вернуться и на которую можно ссылаться.

SafeSort · Этап 8 из 8
Идея→Проект→Код→Безопасность→Дубликаты→Тесты→GitHub→Релиз

Проект готов, проверен тестами и подключён к автоматической проверке. Мы закончили первую пригодную для использования версию SafeSort. Теперь ей нужен номер, чтобы отличать её от будущих изменений — тот самый номер, который мы уже записали в pyproject.toml на странице 23.5, где он был просто техническим полем. Сейчас разберём, что он означает.

Семантическое версионирование

Эта схема называется семантическим версионированием (Semantic Versioning, SemVer) — соглашение о записи номера версии как MAJOR.MINOR.PATCH:

Часть номераМеняется, когда
MAJORнесовместимые изменения — старый способ использования перестаёт работать
MINORдобавлена новая возможность, старое поведение сохранено
PATCHисправлена ошибка, поведение по сути не изменилось
Соглашение, а не закон физики
Семантическое версионирование — общепринятая договорённость, а не встроенное в инструменты правило: ничто технически не мешает нарушить его смысл. Пользы от него ровно столько, сколько сам проект последовательно ему следует — это ориентир для тех, кто устанавливает пакет и хочет понимать, чего ждать от новой версии.

Первая версия SafeSort — 0.1.0: минорная версия ниже 1 традиционно означает «интерфейс ещё может измениться без отдельного согласования».

CHANGELOG — что изменилось в этой версии

CHANGELOG.md
## [0.1.0]

### Added

- scan, plan, apply, duplicates, undo commands

### Safety

- dry-run by default (scan/plan/duplicates never modify files)
- no automatic duplicate deletion
- no silent overwrite of existing files
CHANGELOG описывает только реальные версии
Придумывать историю более ранних версий, которых не существовало, — не задача CHANGELOG: он честно описывает то, что действительно вышло, начиная с первой настоящей версии проекта.
GitHub Release строится поверх тега — здесь честно о том, чего нет

Тег и релиз — а почему их здесь нет

Тег (tag) — постоянная метка на конкретном коммите, обычно соответствующая номеру версии. Релиз на GitHub строится поверх тега и добавляет к нему описание изменений — то же содержание, что и в CHANGELOG, но в формате, который видно прямо на странице репозитория:

Терминал (как это делается — не для этого репозитория, см. ниже)
git tag v0.1.0
git push origin v0.1.0
SafeSort подготовлен к версии 0.1.0 — но тег и релиз для этого курса не создавались
SafeSort живёт внутри projects/python/safesort/ — подкаталога общего репозитория курса python-from-zero, а не отдельного репозитория. Тег версии в Git относится ко всему репозиторию целиком, а не к одному подкаталогу — поэтому git tag v0.1.0 здесь означало бы «версия 0.1.0 всего курса», а не «версия 0.1.0 SafeSort», и было бы вводит в заблуждение. SafeSort подготовлен к релизу — версия зафиксирована в pyproject.toml, изменения описаны в CHANGELOG.md, тесты проходят, — но реальный тег и GitHub Release имеет смысл создавать только в отдельном репозитории, если SafeSort когда-нибудь в него переедет.
Публикация в PyPI — осознанно за рамками версии 0.1.0
Установка через pip install -e . достаточна для разработки и личного использования. Публикация пакета в PyPI, чтобы его можно было установить командой pip install safesort без ссылки на репозиторий, — отдельная тема с собственными требованиями к учётной записи и публикации, и версия 0.1.0 сознательно её не касается.

Коротко

  • MAJOR.MINOR.PATCH — соглашение о номере версии, а не встроенное в инструменты правило.
  • CHANGELOG.md описывает только версии, которые действительно вышли.
  • Тег версии относится ко всему репозиторию — для проекта внутри общего репозитория курса это значит, что тег и GitHub Release для SafeSort 0.1.0 сознательно не создавались.
