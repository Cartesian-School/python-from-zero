От идеи к требованиям проекта

Прежде чем писать код, нужно точно решить, что программа обязана делать — и чего делать не должна.

Проекты предыдущих глав решали учебную задачу и заканчивались, когда работали правильно. SafeSort устроен иначе: это первый проект главы, который доводится до состояния, в котором его можно опубликовать на GitHub, установить командой pip install и показать другим людям как часть портфолио. Прежде чем писать код, нужно точно сформулировать, что программа обязана делать — и, не менее важно, чего она делать не должна.

SafeSort — локальная программа командной строки, которая наводит порядок в каталоге с файлами: раскладывает их по категориям (документы, изображения, архивы и так далее) и находит файлы с одинаковым содержимым. У задачи есть особенность, которая определяет всю архитектуру программы: SafeSort работает с настоящими файлами пользователя, а значит, ошибка в программе может стоить кому-то реальных данных.

Функциональные требования

Функциональные требования описывают, что программа должна уметь:

  • сканировать каталог и находить в нём файлы;
  • классифицировать каждый файл по расширению;
  • строить план перемещений, не трогая диск;
  • выполнять перемещения только по явной команде;
  • находить файлы с одинаковым содержимым;
  • отменять последнюю выполненную операцию.

Нефункциональные требования

Нефункциональные требования описывают не «что», а «как» — свойства, которым должна отвечать программа независимо от конкретной команды:

  • поведение по умолчанию не должно изменять файлы пользователя;
  • программа никогда не перезаписывает существующий файл молча;
  • результат работы предсказуем: одинаковый ввод даёт одинаковый план действий;
  • вся обработка происходит локально, без сети;
  • логику можно проверить автоматическими тестами без реальных файлов пользователя.
Программа по умолчанию ничего не меняет
Это не пожелание, а главное архитектурное решение проекта. Команды scan, plan и duplicates только читают файловую систему. Переместить файлы может исключительно команда apply — и никакая другая команда не должна перемещать или удалять файлы неожиданно для пользователя.

Что сознательно остаётся за рамками версии 0.1.0

Формулировка границ проекта так же важна, как список того, что он делает — иначе проект разрастается быстрее, чем его успевают довести до рабочего состояния:

Не входит в версию 0.1.0Почему
Автоматическое удаление дубликатовУдаление данных без явного подтверждения — риск, а не удобство
Графический интерфейсКомандная строка проще реализовать, протестировать и объяснить
Загрузка файлов в облакоПрограмма работает только с локальной файловой системой
Классификация по содержимому файлаКлассификация по расширению уже решает основную задачу
Сетевой сервисSafeSort — инструмент для одного пользователя на одной машине

От требований к плану работы

Требования выше определяют пять команд SafeSort — scan, plan, apply, duplicates, undo — и то, в каком порядке имеет смысл их реализовывать: сначала то, что только читает файловую систему, затем то, что её меняет, и только потом — поиск дубликатов и отмену операций. Разделы 23.7-23.16 следуют именно этому порядку.

Коротко

  • Функциональные требования описывают, что программа делает; нефункциональные — какими свойствами обладает её поведение.
  • Явная граница «что не входит в версию» защищает проект от бесконечного разрастания.
  • Главное нефункциональное требование SafeSort: команды чтения (scan, plan, duplicates) никогда не меняют файлы, перемещение делает только явная команда apply.
